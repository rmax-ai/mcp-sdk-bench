## Interoperability (SPEC.md §8 INTEROPERABILITY, M2.2)

Cross-implementation pairings, each a real client from one SDK against a real server from another SDK in a fresh subprocess world. **Every cell below is run-verified** by `tests/interoperability/test_pairings.py` (connect/initialize, 6-tool discovery, get_ticket + probe_schema round-trip, clean teardown) and `tests/interoperability/test_version_negotiation.py` (wire-level protocolVersion evidence via the log-mode stdio proxy in `tests/conformance/helpers.py`). Protocol versions are captured from the wire, not SDK self-reporting. Machine-readable output: `results/latest/interoperability.json` (regenerated by `uv run mcpbench interop`).

| Pairing | Status | Negotiated protocolVersion (client-announced → wire) | Wire-level note |
|---|---|---|---|
| FastMCP client → FastMCP server | ✅ pass | 2026-07-28 → 2026-07-28 | FastMCP 4.0.2 opens with the modern `server/discover` probe (no legacy `initialize` on the wire); both sides run 2026-07-28. |
| FastMCP client → official server | ✅ pass | 2026-07-28 → 2026-07-28 | Official mcp 2.1.1 server answers `server/discover` with `supportedVersions: ["2026-07-28"]`; the client stamps 2026-07-28 on subsequent requests. |
| Official client → FastMCP server | ✅ pass | 2025-11-25 → 2025-11-25 | Official mcp 2.1.1 client offers `LATEST_HANDSHAKE_VERSION` (2025-11-25) on `initialize`; the FastMCP 4.0.2 server accepts it. |
| ADK client → FastMCP server | ✅ pass | 2025-11-25 → 2025-11-25 | ADK 2.8.0 embeds the mcp 1.29.1 client; legacy handshake at 2025-11-25 against the mcp 2.x-era FastMCP server negotiates cleanly. |
| ADK client → official server | ✅ pass | 2025-11-25 → 2025-11-25 | Same mcp 1.29.1 handshake against the official mcp 2.1.1 low-level server; no negotiation failure. |

Non-pass cells: none. Two honest caveats, both run-verified rather than hidden:

- **ADK client pairings see tools only.** `McpToolset` has no first-class MCP resource/prompt surface (M1 finding), so `resources_seen`/`prompts_seen` are 0 for ADK client rows — absence of a client surface, not a server deficiency (both servers serve the deployment-policy resource and incident-triage prompt, proven by the FastMCP/official client rows).
- **ADK protocol versions are proxy-captured.** `McpToolset` exposes no initialize result, so the ADK rows' versions come solely from the wire log (harness limitation, recorded as `exposes_protocol_version=False` in `tests/conformance/helpers.py` DISCOVERY_CONTRACT).

## Elicitation and multi-round-trip (M3.1, SPEC.md §18)

The world owns two elicitation policies (`world/state.py`): `reserve_inventory` without an employee requests a **clarification**; `deploy_service` to production requests an explicit **approval**. The server variant owns the protocol mechanics behind the callback — that split is the §18 measurement (application code identical across variants; only protocol code differs). Run-verified by `tests/interactive/` (hermetic world-seam tests, real stdio pause/resume per adapter, agent-loop pause/resume with the scripted user simulator) and `datasets/interactive.jsonl` (categories F/G).

| SDK | Elicitation (server→client) | Protocol mechanics | Evidence |
|---|---|---|---|
| official (mcp 2.1.1) | ✅ supported | Imperative `elicitation/create` via `ServerSession.elicit_form`; the server handler awaits the answer **in-band** and the same wire call completes. Client advertises `ElicitationCapability` (form mode) at initialize. | `tests/interactive/test_elicitation_adapters.py` (clarify/approve/decline pause-resume), [spec](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation) |
| fastmcp (4.0.2) | ✅ supported (guard pattern) | Imperative `ctx.elicit()` is **unavailable** on the 2026-07-28 connection FastMCP pairs negotiate (SEP-2577 removed the in-call back-channel). The supported path is SEP-2322: the tool returns `InputRequiredResult` with an embedded `ElicitRequest`; the FastMCP client drives it through the registered elicitation handler and **retries the call** with `input_responses` (extra wire leg, counted in `MCP_round_trips`). Output schema pinned via `server.tool(output_schema=...)` so the union return type cannot leak. | `tests/interactive/test_elicitation_adapters.py` (same three flows), [fastmcp elicitation docs](https://gofastmcp.com/servers/elicitation) |
| adk (2.8.0) | ❌ unsupported (over MCP) | No request-context injection point at which an ADK `FunctionTool` could suspend on `elicitation/create`; a missing employee surfaces the world's honest WorldError, production deploys keep the legacy guard. Client-side `McpToolset(elicitation_callback=...)` exists but is deliberately unwired (SPEC.md §23 one-independent-variable). Framework-native equivalents outside MCP: `FunctionTool(require_confirmation=...)`, `LongRunningFunctionTool`. | `tests/interactive/test_adk_elicitation.py` (adk env only), [ADK confirmations](https://google.github.io/adk-docs/tools/confirmation/) |

Multi-round-trip accounting: `round_trips` counts LLM-driven tool loops; `mcp_round_trips` adds the elicitation pause/resume legs (one per elicitation — the resumed call crosses the wire again on FastMCP, completes in-band on official). `user_interactions` counts scripted-simulator answers (clarify-hook injections + elicitation responses). Clients without the elicitation capability degrade honestly: the world falls back to its pre-M3.1 legacy policy (`ElicitationUnavailable`), never a faked answer — run-verified by the existing `tests/conformance/test_errors.py` suite, which exercises both servers with capability-free clients.
